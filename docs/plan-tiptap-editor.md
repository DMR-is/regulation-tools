# Editor v2 on Tiptap

Status: **phases 0–3 done**; trial in the apps (phase 4) on
`1.0.0-next.2`, which closes the alt-text gap (exit criterion 6). PR #7,
reviewed; see *Review of PR #7* below.

The goal is to replace the TinyMCE 5 editor (end-of-life since April 2023) with
one built on Tiptap/ProseMirror, losing no functionality and no content. The
two halves of the work are an editor at feature parity and a test harness that
proves, on real regulations, that nothing is lost.

## Ground rules

1. **HTML stays the storage format.** The editor loads HTML and emits HTML.
   `cleanupEditorOutput`, `dirtyClean`, `getDiff`, `getStructuredDiff`,
   `useTextWarnings` and the database are not touched by the migration.
   Tiptap's JSON never leaves the editor.
2. **Never drop content silently.** ProseMirror discards whatever its schema
   does not describe, and does so without complaint. So the schema is built
   from what the corpus actually contains (below), and every load is checked:
   if parsing changed the document beyond the known, allowed normalizations,
   the editor says so instead of quietly saving a damaged text (see
   *Fidelity guard*).
3. **Side by side, then switch.** v2 ships as a new entry point
   (`@dmr.is/regulations-tools/EditorV2`) next to the current `Editor`.
   Consumers opt in per screen. TinyMCE is removed in a later major version,
   once v2 has been used for real.
4. **The corpus decides.** "Done" means the round-trip harness passes on a
   broad sample of real regulations, not that the editor looks right on a
   handful of documents.

## Schema: what real regulations contain

Census by `scripts/editorCorpus.ts` (October 2026): 700 regulations sampled
across every decade from 1910 to 2020 (`current`, plus `original` when amended),
1,234 documents (869 main texts, 363 appendixes, 2 comments). Numbers are
documents in which the item occurs at least once. The full counts, with
example documents for each, are in `.cache/editor-corpus/census.json`.
Texts come from the public API, which only splits each stored text into main
text, appendixes and comments (`extractAppendixesAndComments`); that is the
text the editor receives when an amendment is edited.

**Blocks at the root:** `p` (1,226), `h3` (945), `ol` (425), `h2` (191),
`table` (156), `hr` (10), `ul` (5), `h4` (3). Nothing else, and no loose
text.

**Inline:** `strong` (968), `em` (914), `br` (351), `sup` (62), `sub` (36),
`a` (35), `u` (26), `img` (20), `font` (3).

**Tables:** only `table > tbody > tr > td`. No `thead`, `th` or `caption`.
`colgroup`/`col` in 5 documents, with no attributes. Cells hold `p`, `br`,
`strong`, `em`, `sup`, `sub`, `u`, `img`.

**Nesting worth noting:** `li > p` (88), `li > ol` (76), `li > ul` (3),
`li > table` (6), `td > p` (43), `strong > br` (72), `em > br` (5),
`h2 > strong` (5), `sup > a` and `a > sup`, `sup > sup` (1).

**Classes:** `h3.article__title` (941, `--provisional` 76),
`em.article__name` (316), `p.Dags` (618), `h2.chapter__title` (185),
`em.chapter__name` (178), `p.FHUndirskr` (185), `table.layout` (86),
`p.indented` (66), `table.layout--list` (37), `h2.section__title` (4),
`em.section__name` (2), `h2.subchapter__title` (4), `p.Undirritun` (3),
`sup.footnote-reference` (2), `sup.footnote__marker` (1).

**Attributes:** `align=center|right` on `p` (974/687), `td` (77/14), `h2`
(7), `h3` (4), `h4` (1); `ol[type=a|i|A]` (220/16/16), `ol[start]` (20),
`li[value]` (33), `ul[type=square]` (1); `td[colspan]` (43),
`td[rowspan]` (15); `a[href]` (35); `img[src|alt]` (20),
`img[width|height]` (11); `p[id]` (2), `strong[id]` (1).

**Not found anywhere:** inline `style`, HTML comments, `span` (so no
`span[data-legacy-indenter]` either), `div`, `section`, `b`/`i`, `data-*`
attributes, table headers.

**Schema (phase 1, `src/_editorV2/schema.ts`).** Built from cleanup's
attribute allow-list (`removeUnwantedAttributes` in
`_cleanup/cleanup-utils.ts`), which defines what the stored format can hold,
checked against the census: whatever cleanup keeps, the editor keeps. So it
also covers things the sample did not contain: legacy indenter spans,
`margin-left`/`text-indent` indents, `data-autogenerated`, `blockquote`,
`th[scope]`, `h2.appendix__title`.

**Fidelity over the corpus (`scripts/editorFidelity.ts`):** 1,214 of 1,234
documents are lossless (the editor round trip, after cleanup, equals cleanup
alone, byte for byte). The text is unchanged in all 1,234. The other 20
differ only in markup, all of it the allowed changes below. A second save
through the editor adds nothing in any document. Median 13 ms per document
in Node (jsdom), max 4 s (0112/2012).

**Allowed changes** (no text or formatting lost; pinned in
`src/__test__/editorV2Fidelity.test.ts`):

- **Nested inline formatting is written in one order** (12 documents), for
  example `<u><strong>` as `<strong><u>`. ProseMirror writes marks in schema
  order, so whichever order is chosen, texts using the other change. The
  order follows the majority in the corpus: `strong` outside `em` (15
  documents against 4), `sup` outside `a` (6 against 1); `strong`/`u` is
  split 8 to 7.
- **`colgroup`/`col` without widths are dropped** (5 documents).
- **`font` is unwrapped, keeping its text** (3 documents, all empty
  leftovers with no attributes).

**Fixed along the way** (each found by the corpus run):

- A list item holding only a nested list (`<li><ol type="a">…</ol></li>`,
  5 documents): Tiptap's list item needs a paragraph first and moved the list
  out. List items now accept any block first.
- A double `<br>` in a list item (10 documents): the editor wraps a list
  item's text in a `<p>`, and cleanup splits a `<p>` at a double `<br>`, but
  not loose text. The editor's output now writes a lone, attribute-free
  paragraph in a list item or cell without its `<p>`, as TinyMCE did
  (`src/_editorV2/serialize.ts`).
- `<sup><a>` footnote links came out as `<a><sup>` (6 documents): links now
  sit inside other marks.
- `<sup class="footnote__marker"><sup class="footnote-reference">` (1
  document): the marker is a mark type of its own, as one mark type cannot
  nest in itself.
- Tiptap's table writes a `<colgroup>` and width styles, and its link adds
  `target` and `rel`: both overridden, so the output holds only what the
  stored format has.

**Found in cleanup, unchanged:** cleanup is not stable around legacy
indenters. Run on its own output it adds a space on each side once
(`a\n<span data-legacy-indenter>…</span>\nb` → `a \n…\n b`), then stops
changing. The current editor behaves the same, and none of the corpus
documents have these spans, so the editor matches cleanup here rather than
correcting it.

**Rule for anything the census finds:** each element/class/attribute either
gets schema support, or gets an explicit, tested normalization that is listed in
this document, for example "`b` becomes `strong`" (already done by
`cleanupEditorOutput`). Nothing is left to ProseMirror's silent default.

## Fidelity guard

A small function, used by both the harness and the editor at runtime:

```
fidelity(inputHtml) → { ok, losses: [{ kind, selector, before, after }] }
```

It parses `inputHtml` into the schema, serializes it back, runs both sides
through the existing normalization (`cleanupEditorOutput`), and compares:

1. **Text:** the whitespace-normalized text content is identical.
2. **Shape:** the per-block element tree with `type`, `start`, `class`,
   `align`, `colspan`, `rowspan` is identical. This reuses the `shape` idea from
   `src/_structuredDiff/`.
3. **Idempotence:** a second round-trip changes nothing.

This is not an HTML validity check. It catches markup that is valid but that
the editor does not know, which would be dropped or changed on load: an
unknown class, an attribute, a `span` wrapper.

**Decided: warn only, never block saving.** A failed check on load shows a
warning in the existing warnings panel naming what would be lost. TinyMCE
changes markup on load today without saying anything, so this is already an
improvement. Saving after the warning makes the loss permanent, as it does
today.

## Long texts: speed

Editing very long regulations is slow and janky today. The largest in the
cached sample is 0112/2012: about 520 KB of HTML and 4,700 elements. The
editor library is only part of the cause. On every change, the current code
path also does all of this on the main thread:

1. **The whole document is serialized on every keystroke.**
   `@tinymce/tinymce-react`'s `onEditorChange` calls `editor.getContent()`
   for each input event, and `Editor.tsx` stores the result. For a 520 KB text
   that is a full DOM-to-HTML pass per key press.
2. **The diff runs synchronously** one second after typing stops (`getDiff`
   in `diffDebouncer`). On long texts it freezes the page mid-sentence. The
   `slow` flag that switches to manual "Endurreikna breytingar" is the
   existing workaround.
3. **The warnings re-parse the whole text** (`useTextWarnings` on
   `debouncedCurrentText`).
4. **The diff pane is replaced wholesale** (`HTMLDump`), so the browser
   re-lays out a second full copy of the document.

ProseMirror helps with the editing itself: a keystroke is a small transaction
that updates only the DOM nodes it touched. Its document model makes it
cheap to know *whether* something changed without serializing anything. But
v2 is only faster if points 1–4 are fixed too. A Tiptap editor that calls
`getHTML()` on every update has the same problem as today. So:

- **Serialize lazily.** `onChange` only flags the editor as dirty.
  `valueRef.current()` calls `getHTML()` when someone asks, and the debounced
  diff/warnings step serializes once per pause, not once per key.
- **Don't re-render React per keystroke.** Tiptap's React binding can be
  told not to re-render on every transaction; the toolbar subscribes only to
  the state it shows (active marks, current block type).
- **Keep the diff off the typing path.** Using `getStructuredDiff` already
  makes it cheaper. On top of that, run it in idle time and cancel it if
  typing resumes. A Web Worker is the last resort: `getStructuredDiff` needs a
  DOM, so a worker would need a light DOM implementation. That is measured
  before it is decided.
- **Only redo the work for what changed** (see *Incremental work*).
- **Warnings from the document, not the HTML,** where that is cheap. Most
  warnings are "find nodes of kind X", which can be answered from the
  ProseMirror document and recomputed only for the changed range.

**Measure, don't guess.** `scripts/editorSpeed.ts` types into the longest
texts in Chromium and reads the browser's own timings: time to load, delay
per keystroke, and the longest main-thread block while typing and after a
pause. v2 must meet the targets below, and the same script then guards
against regressions.

**How it got there** (each step measured):

1. The editor alone, with the full `getStructuredDiff`: typing was already
   fixed (0–1 slow keys), and the freeze after typing fell to 137–462 ms.
2. The incremental differ (`createStructuredDiffer`): diffs after an edit
   take 1–6 ms in Node instead of 100–430 ms; the freeze after typing fell
   to none on four texts.
3. The first key after each pause was slow (~100 ms): EditorV2's state
   change re-rendered the editor frame, which hands Tiptap fresh options.
   The frame is now memoised with stable callbacks.
4. The 0801/2022 appendix is one section (no articles), so its pane part is
   the whole appendix. The pane now replaces only the changed blocks within
   a part, which took its freeze from ~200 ms to none.

somewhat slower; only typing in a paragraph is measured (paste, adding
articles and table work are for the phase 3 browser tests); the five texts
are the heaviest in the corpus. Load on the largest text (2.5 s at 4×) is
mostly loading 520 KB into ProseMirror and was not a target.

`Editor`: ~850 ms). Adding articles inside an article-less appendix is
unusual; making it cheaper means moving DOM nodes between sections.

Before the pane kept unchanged sections in place (commit 088d09d), the
freeze after a paste or a new article was 250–470 ms on every text.

## Incremental work: only what changed

A keystroke changes one paragraph in one article. Today, every step after it
handles the whole document again: serialize, parse, diff, render the pane.
ProseMirror makes it cheap to know what did *not* change, because its
documents are immutable: an unchanged top-level node is the same object
before and after a transaction. Each step uses that:

1. **Serialize.** Cache the HTML per top-level node in a `WeakMap` keyed by
   the node. `valueRef.current()` and the diff only serialize the nodes that
   are new, and join the rest from the cache.
2. **Base side, parsed once.** The base text does not change while editing,
   so `parseSections(older)` runs once per editor session, not once per diff.
3. **New side, parsed per section.** Only sections whose HTML changed are
   parsed again; the others keep their `Section` objects from the last run.
4. **Section diffs reused.** `diffBlocks` (the htmldiff part, which is the
   expensive one) is cached per (old section, new section) pair. An unchanged
   article pairs with the same old article as before and reuses its result.
   The similarity cache already in `getStructuredDiff` persists across runs
   instead of starting empty each time.
5. **Global steps stay global.** Section alignment and move detection look
   at the whole document, because an edit in one article can make it pair
   with a different old article, or reveal a move. They run every time over
   the cached sections. They are cheap when titles match, but this is
   measured, not assumed. `detectMoves` changes the ops it is given, so cached
   ops must be copied before it runs, or it is changed to return new ops.
6. **Pane updated per section.** The diff pane renders one keyed element per
   section, so React only replaces the articles whose diff changed, instead of
   setting the whole pane's `innerHTML`.

**Where it lives.** A new API next to `getStructuredDiff`, for example
`createStructuredDiffer(older, opts)` returning `diff(newer)`, which keeps the
caches between calls. It works by comparing section HTML, so it needs nothing
from Tiptap and is tested in Node like the rest. The editor can optionally
pass a hint saying which sections changed, to skip even the comparison.
`getStructuredDiff` stays as it is.

**Correctness guard.** The incremental result must equal a full
`getStructuredDiff` run, byte for byte. A test takes corpus documents,
applies sequences of random edits (type in a paragraph, delete a paragraph,
add an article, rename one, move one), and compares the two after every edit.
If they ever differ, the cache is wrong, and the test names the edit sequence
that caused it.

## Tests

### 1. Unit: schema round-trips (Jest, Node)

- Fixtures in `src/__test__/editorV2/`: one small HTML file per construct in the
  census (each class, each list type, `li[value]`, merged cells, images,
  signatures, provisional articles) plus the existing
  `cleanEditorOutput/input/*.html`.
- Each fixture must pass `fidelity`. Parsing and serializing in Node needs a DOM
  (`@tiptap/html` server variant, or jsdom as the cleanup code already uses);
  phase 1 confirms which works under Jest.
- Every allowed normalization gets a test that pins it.

### 2. Corpus: round-trip on real regulations (script)

`scripts/editorRoundTripCorpus.ts`, built and run like
`scripts/structuredDiffCorpus.ts`, using the same polite client
(`scripts/regulationsApi.ts`: sequential, one request a second, cached).

- **Sample:** wider than the diff corpus, spread across decades, plus a fixed
  list of known difficult texts (large tables, old texts with legacy
  indenters, image-heavy ones).
- **Request budget: about 1,000 requests in total**, agreed with the API
  owners. With `original` + `current` per regulation, that is roughly 450
  regulations plus the listing requests. The budget is a `--max-requests`
  flag, and the script stops when it is used up. Responses are cached, so
  reruns while fixing the schema make no new requests.
- **Checks per document:** `fidelity` passes; no exception; parse time under a
  limit (large texts are where ProseMirror can feel slow).
- **Untouched save is empty.** Loading a text and saving it without edits,
  through `cleanupEditorOutput`, must give byte-identical output. Otherwise
  every save writes noise into `regulationchange.changeset`, which
  reglugerd-admin-www fills with a line-based `diff -u` of the stored text
  (`src/utils/diffing.ts`, `createPatch`).
- **Output:** a JSON report grouped by loss kind and selector, so one schema
  fix can be checked against every document it affects, plus a summary line
  (`N/M lossless`).
- **Census mode:** `--census` prints the element/class/attribute counts used
  above, so the schema can be checked against new data at any time.

The corpus run is the acceptance gate: **100% lossless, or every remaining
difference is an allowed normalization in this document.**

### 3. Paste and Word import (Jest)

- Capture real clipboard HTML from Word (Windows and Mac), Google Docs and the
  current reglugerd.is pages, plus a set of real `.docx` files, as fixtures.
- The shared paste pipeline gets plain unit tests (it is just functions), and
  the result must pass the schema without loss.
- Comparison test: v1 pipeline output and v2 pipeline output are identical
  before insertion. They should be, since the functions are shared.

### 4. Browser: interactions (Playwright)

Fewer tests, for what only a real browser shows: applying each block format
from the toolbar, the "m. heiti" commands, table class changes, paste into the
middle of an article, image upload placeholder → URL, undo after paste, and
warnings highlighting the right element. One test per row of the parity
checklist that involves interaction.

### 5. Side by side on real work

Before v1 is retired, let editors use v2 on real amendments for a period, and
compare saved output with what v1 would have saved (diff via
`getStructuredDiff`; formatting-only changes show up as `data-diff-change="format"`).

   doing so.

**Found while testing:** on React 19 the current editor takes about 300 ms
longer to appear (0340/2017: 0.70 s against 0.40 s on 18; 0112/2012: 1.3 s
against 1.0 s). It is React 19's `Suspense` behaviour: once a fallback has
been shown, React holds the content back for up to 300 ms. `Editor` loads
`EditorFrame` with `React.lazy` inside `Suspense`; without the lazy loading,
both versions load in about 0.5 s. It is not caused by this change: island.is
and official-journal-web already run the current editor on React 19. v2
loads its editor code without a `Suspense` fallback (a dynamic import in an
effect, or a preloaded chunk) to avoid it.

**Making sure nothing else stops working:**

- `tsc` and the Jest suite pass with React 19 types.
- `tsc` also passes against the React 18 types. React 18 stays supported
  (reglugerd-admin-www runs 18.3.1, on Next 15), and developing on 19 makes
  19-only APIs (`use`, `useActionState`, `useOptimistic`, `ref` as a plain
  prop) type-check here while breaking there. The package does not bundle
  React (`build.js`, `bundle: false`), so the consumer's React is what runs.
  `yarn typecheck:react18` (part of `yarn build`) runs `tsc` with
  `tsconfig.react18.json`, which maps `react` and `react-dom` to the React
  18 types, installed under the `types-react-18` / `types-react-dom-18`
  aliases, and turns off automatic `@types` so React 19's are not loaded
  too.
- The speed harness (`scripts/editorSpeed.ts`) doubles as a smoke test of the
  current editor in a real browser: it loads, typing lands in the text, and
  the diff pane updates. It runs once on React 18 and once on React 19
  before the release.
- A pre-release is tried in reglugerd-admin-www (React 18) and in one
  island.is screen (React 19) before the release (see *Releases*).

## Decisions

- **Fidelity check:** warn only, never block saving.
- **Corpus:** about 1,000 API requests at most, one a second, cached. If the
  results are not convincing, ask before going further; another ~1,000 is
  likely fine.
- **`config`:** replaced by a typed `toolbar` prop; consumers only used
  `config` for the toolbar.
- **Diff pane uses `getStructuredDiff`, not `getDiff`.** It is expected to
  replace `getDiff` before v2 goes live, and it suits the editor's case: the
  edited text is mostly identical to the base, and unchanged articles
  short-circuit on equality (0678/2009 · 0785/2014: 139 → 53 ms; the
  690-item list in 0544/2015 diffs only the changed item). The pane only
  displays the diff. The diff that is saved on an impact is computed by the
  consumer, so this choice does not change what gets saved. **v1's pane keeps
  `getDiff`**; the switch ships with v2, as part of its release.
- **Incremental work is part of v2**, not an optional later step (see
  *Incremental work*).
- **Semantic formats, a mix:**
  - *Node types* for the headings, which are the regulation's structure:
    `articleTitle` (Grein, with `--provisional` for Bráðabirgðaákvæði),
    `chapterTitle` (Kafli), `subchapterTitle` (Undirkafli), `sectionTitle`.
    Each one holds its own `em.*__name`, and is meant for
    the top level. The schema still accepts them elsewhere, so a text that
    has one inside a list or cell loads unchanged (none in the corpus); the
    editor's commands only create them at the top level, and the
    `nonRoot*Titles` warnings stay.
  - *A class allow-list* on the ordinary paragraph for the variants that are
    only styling: `indented`, `Dags`, `FHUndirskr`, `Undirritun`.
  - The HTML output is the same as today either way. If the heading rules turn
    out too strict for real texts, the corpus run will show it as fidelity
    losses, and the rule is loosened rather than the text changed.

- **Versions:** 1.0.0 for this release, trialled as `1.0.0-next.N`;
  2.0.0 removes TinyMCE.
- **Right-click menu on tables:** only if editors ask for it during the
  trial.
- **Behaviour that differs from `Editor`:** approved (see the checklist).
